# 6:4 双轨分配机制

本文档说明 AlphaSplit 在「贡献计量」与「绩效分配落地」之间的产品边界，并与课题立项文档中的「协商锚点 + 人工确认」框架对齐。

---

## 1. 与立项文档的关系

课题立项描述（2026-08-12）规定：

- 系统输出 **贡献系数 + 归因解释**，作为 **协商锚点**，而非最终裁决；
- 保留 **人工确认** 环节，规避「自动发薪」的合规与伦理风险；
- 与 KPI / 主观评议对照，提供可解释、可追溯的量化证据。

立项文档**未规定**具体分钱比例。本项目的 **6:4 双轨制** 是在上述框架下的**落地产品设计**：在尊重机构既有制度的前提下，将夏普利证据渐进接入考核分配。

---

## 2. 双轨定义

对可分配利润（或奖金池）`P`，各角色 `i` 的最终份额为：

```text
最终份额_i = 60% × 现行份额_i + 40% × 夏普利新池份额_i
最终金额_i = 最终份额_i × P
```

| 轨道 | 比例 | 含义 | 数据来源 |
|------|------|------|----------|
| **旧池** | 60% | 沿用机构提交的**现行分配方案**（制度、历史惯例、HR 既定比例） | 用户录入 / 机构档案 |
| **新池** | 40% | 按 HS300 回测 **夏普利边际贡献** 动态分配的证据建议 | `query_engine` 回测输出 `role_breakdown.weight` |

要点：

- **旧池 60%**：系统不替机构重写历史制度，只读取并保留用户现行方案；
- **新池 40%**：仅计量五投研角色（行业 / 个股 / 策略 / 量化 / 风控）在 Pipeline 内的边际贡献；
- **合成结果**：供考核与分配**讨论参考**，须经人工确认后落账。

可选：新池内部可叠加 HR 调节系数 `role_weights`（API 已支持），用于体现「制度偏好」对证据权重的调节。

---

## 3. 与回测引擎的对应关系

| 模块 | 职责 |
|------|------|
| `backtest/query_engine.py` | 计算**新池 40%** 内各角色权重（夏普利 → 归一化） |
| `backtest/main_quantskills.py` | 完整 6:4 合成示例（含基金经理等非动态角色旧池权重） |
| `engine/web/app.js` | 人工确认页展示旧池 / 新池 / 合成表，支持编辑现行份额 |

回测结论页侧重 **证据生成**（新池建议 + 夏普利排名）；**6:4 合成表** 放在 **人工确认** 主舞台。

---

## 4. 演示默认参数

Web 演示在无机构档案时采用：

- 奖金池示例：`¥10,000,000`
- 旧池现行份额：五角色**均等 20%**（可编辑，合计应为 100%）
- 新池份额：取自最近一次 HS300 回测的 `role_breakdown[].weight`

机构落地时替换为真实现行方案即可，公式不变。

---

## 5. 路演话术（可直接引用）

> 我们不是用夏普利全盘推翻既有制度。  
> **60% 沿用贵司现行分配，40% 按真实回测证据动态校正**；  
> 系统给出合成建议与完整证据链，**人工确认后**方可应用——  
> 这与立项中的「协商锚点 + 人工确认」一致，是把证据接进制度，而不是自动发薪。

---

## 6. 产品流程

```text
HS300 多角色回测
    → 夏普利贡献 + 新池 40% 建议权重（回测页）
    → 录入 / 确认现行份额（旧池 60%）
    → 6:4 合成表 + 金额（人工确认页）
    → Agent 协商 / 带宽夹入（可选附录）
    → 人工确认落账
```
